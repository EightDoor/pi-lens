## Verdict: NEEDS CHANGES

Claims 1 (#3587) and 2 (heartbeat on the tail) hold up under attack. Claim 3
(the exit-listener release) does not fix the symptom it cites. The vitest fork
workers are killed with SIGTERM, and Node emits no `exit` event on a
default-signal death. I reproduced the dead-pid lock on the head. Findings 1
and 4 are behaviour or test-guard findings, so a verify round is needed.

## Findings

### Spec compliance

**F1 (behaviour, blocking for scope addition 2): the exit listener never runs
on the path that leaves the dead-pid lock.**
`clients/instance-registry-lock.ts:128-132` registers
`process.on("exit", releaseOpenHoldsBestEffort)`. The PR body and
`.changelog/3518-registry-lock-exit-release.md` say the worker exits "via a
forceful `process.exit()`". It does not.
- tinypool's `terminate()` and vitest's fork `stop()` both call `fork.kill()`,
  which sends SIGTERM (`node_modules/vitest/dist/chunks/index.DzobfTyw.js:11056`).
- vitest's own comment at `node_modules/vitest/dist/chunks/init.3UJvPvQg.js:400`
  says: "forks are SIGTERM'd and never reach Node's exit-time flush".
- `tests/index-wiring.test.ts` contains no `process.exit`.

Probes, all on the head build:

| Probe | Result |
|---|---|
| Forked child holds the lock (op never resolves), then calls `process.exit(0)` | `locks: lock.1,lock.1.released`, `legacy: 11256 …`: generation released |
| Same child, parent sends SIGTERM | `child exit null SIGTERM locks: lock.1 legacy: 11285 …`: nothing released |
| Throwaway vitest test with a fire-and-forget `withInstanceRegistryLock` hold, `--pool=forks` | `lock.1` unreleased, owner 28083 `alive=n`, legacy lock `28083 …` |
| `tests/index-wiring.test.ts --pool=forks`, fresh `PI_LENS_HOME`, 3 runs | run 1: `top=lock.18 released=NO owner=6345 alive=n legacy=6345 …`; runs 2 and 3 clean |

- **The fixer's 3/3 clean runs were chance.** Whether a leak happens depends on
  whether a fire-and-forget mutation is still in flight when the SIGTERM lands.
- **It also leaks between test files.** My pre-fix probe C shared one
  `PI_LENS_HOME` with earlier head-code runs, and the witness golden went red
  on `+ instance-registry-lock-stale-takeover`. That row comes from a dead-pid
  generation a prior worker left.
- **Nothing records that the listener ran.** It is a new seam with no pushed
  record, so no log could have shown it failing to fire.

Remedy: drop scope addition 2 from G16 (commit b91754357, its fragment and its
tests) and file it with the correct mechanism.
- The likely test-side fix is to drain the registry tail at file teardown,
  for example `afterAll(() => _settleRegistryMutationsForTests())` in
  `tests/index-wiring.test.ts` or in the shared setup. This is a shape I have
  not verified across callers, and the quiet-window heartbeat is also
  fire-and-forget.
- Do not add a production SIGTERM handler: that changes the host's signal
  semantics.
- If the listener is kept for pi's own `process.exit()` paths, the PR body and
  fragment must stop claiming it fixes the index-wiring leak, and F2 and F3
  apply.

**F2 (behaviour, minor; moot if F1 drops the addition): the listener releases
the generation only, not the legacy lock.**
`release()` (`:166-170`) unlinks `instances.json.lock` and then marks the
generation released. `releaseOpenHoldsBestEffort` (`:118-126`) only calls
`releaseGeneration`.
- The `process.exit` probe above leaves `legacy: 11256 1790499563796` owned by
  the dead pid.
- The next writer of this version takes it over silently (a dead pid is stale
  on sight), so nothing breaks today. It is still half of what `release()`
  does, which the docstring's "sync generation release only" hides.
  `releaseLegacyLock` is itself synchronous.
- Fix: track `{ target, hold }` and call `release(target, hold)`.

## Named simplification (not a finding against this PR)

`deregisterInstanceRootNow` runs inside an async tail op that its only caller
fires and forgets (`index.ts:3692`).
- **Why the sync attempt is unneeded.** The "SYNC fs inside" contract comes
  from #234's teardown rule, but the queued op does not run on the teardown
  hook. With the heartbeat now on the tail, the only in-process holder the
  sync attempt can still meet is the reaper's direct `pruneDeadInstances`
  (`clients/instance-reaper.ts:1771`).
- **The simpler shape.** One `withInstanceRegistryLock(…,
  LOCK_WAIT_THROUGH_LEASE_MS)`, using `ownProcessStartIfKnown` if #234 must
  hold.
- **What it removes.** The dual path, `planRootRemoval`'s second caller, and
  Residual 2's 500 ms event-loop block, with no new cross-cutting state.

The orchestrator can file this.

## Cleared under attack

- **(a) The heartbeat on the tail.**
  - `runtime-turn.ts:709` calls it with `void`. `quiet-window.ts:233` awaits
    it, but `runQuietWindow` itself is fire-and-forget (`index.ts:3591`). No
    hook-path await grows, and `hook-await-bounds` is green.
  - There is no re-entrant deadlock: `updateHeartbeatNow`'s repair uses
    `void registerInstance`.
  - The worst-case delay is bounded by the tail op in front, about 5.5 s for a
    lease-wait fallback.
  - Ordering around session replacement improves: a heartbeat queued before
    `deregisterInstance` finds the entry and intent cleared, and does not
    re-register.
  - Residual, not a finding: a hung filesystem promise in any tail op now
    wedges every later heartbeat. Through `runQuietWindow`'s `_inProgress`
    latch it also wedges every later quiet window, including the cascade
    carry-over. Before this PR, only the heartbeat's own I/O could do that.
    Pile-up per turn is one small closure.
- **(b) Owner token.** `releaseGeneration` writes `lock.<g>.released` for its
  own generation number only. After a stale takeover, g is below the top, so
  the marker is inert. This is the same exposure as the normal `finally`
  release, with no new window.
  - Listener registration: once per process across module graphs, probed.
  - It is an `exit` listener, not `beforeExit`, and it is sync-only.
  - It does not interfere with `deregisterInstance`: its `release` deletes the
    hold from the set first.
  - It covers forked workers and MCP servers only under `process.exit` or a
    natural exit, never under a signal (F1).
- **(c) Shapes 10/13/17/18.** The new queued and landed rows go through
  `incrementDegradationCount`. Lock timeouts and failures are recorded by the
  lock. The exit swallow is best-effort at exit. `exitReleaseRegistered` is a
  process-lifetime latch, not session state.
- **#3587 core.** `planRootRemoval`'s generation gate is intact (R3 reds). The
  ungated `rememberRegistrationRoot(undefined)` branches are the safe
  direction. A session replacement during the 5.5 s fallback lands behind it
  on the tail.
