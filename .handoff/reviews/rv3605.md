## Verdict: needs changes

The containment works, and every claimed guard is live: the red run reproduces, and 8 of 8 mutations go red. But two behaviours of the shipped seam are worse than pre-fix for the reporter's own case, and one leaves the per-file degradation silent where the user sees it. ## Spec-compliance findings (issue #3605 and the triage comment)

### F1 (high): a trap that one input causes every time now disables tree-sitter for the whole process, and a restart does not fix it

`reportWasmAbort` counts every distinct trap object against one process budget, whatever input caused it (`clients/tree-sitter-client.ts:622-637`). A trap that always happens on the same file content cannot be told apart from heap damage. Take a file whose content always traps the parser, for example through an OOB bug in a grammar's external scanner. It is never cached, because `treeCache.set` runs only after a successful parse. So every consumer that parses it (facts, the runner, the graph, complexity, read-expansion) re-parses it and spends one budget unit each time. The 4th parse poisons the process and every other file loses tree-sitter. The `markTreeSitterWasmAborted` notice says "Restart ... to recover". A restart does not recover it: the same file poisons the new process after 4 more parses.

Probe: the real client and real python grammar, with `Parser.prototype.parse` throwing a `WebAssembly.RuntimeError` for content containing `BOOM`. Each round parses x.py (traps) and then y.py (healthy):

```
HEAD 72ccc7122:
round1: x.parsed=false y.parsed=true aborts=0 available=true
round2: x.parsed=false y.parsed=true aborts=0 available=true
round3: x.parsed=false y.parsed=true aborts=0 available=true
round4: x.parsed=false y.parsed=false aborts=1 available=false
round5: x.parsed=false y.parsed=false aborts=1 available=false
ledger=[["wasm-trap",3,...],["wasm-abort",1,"3 wasm traps absorbed, next one: memory access out of bounds"]]

pre-fix df5fb8abb (same probe):
round1..round5: x.parsed=false y.parsed=true aborts=0 available=true
ledger=[]
```

`compileQuery` (`:2336`) and `compileRawQuery` (`:2380`) do not cache a failed compile either. So a query that always traps on compile spends the budget on every call in the same way. The PR applies exactly this reasoning to `Language.load` (R7: "one bad grammar must not poison every language") but not to one bad file or one bad query.

Remedy (a sketch; not checked against every caller): key traps by input (language + content stamp, or query source). A repeat trap on an input that has already trapped is charged to that input: it stays not-parsed until its content changes, as R7 does for grammars. Only a trap on a new input spends process budget. At minimum, the PR body's maintainer-decision section must name this case, and the notice must not promise that a restart recovers.

### F2 (high): after a transient trap, the file's symbols stay missing from the graph until someone edits the file

Pre-fix, a trap rejected the build and the next build re-extracted the file. Post-fix, the build commits the trapped file as zero symbols with `extractionCoverage` all `unavailable`. Later builds in the same process reuse that entry while the file is unchanged. The recycle exists so that a later parse can succeed, but nothing ever parses this file again. The reporter's evidence is that the trap is stateful ("direct re-parse of the triggering file in isolation succeeds"), and this is exactly that case.

Probe: real `buildOrUpdateGraph`, trap injected at `Query.prototype.matches` for b.py in build 1 only. Build 2 runs with the same files and no trap, and the workspace cache is kept (same process):

```
HEAD:     trappedBuild=["alpha_fn"]  build2 (no trap)=["alpha_fn"]            <- trap_here_fn still missing
pre-fix:  trappedBuild="REJECTED: memory access out of bounds"  build2=["alpha_fn","trap_here_fn"]
```

With `clearReviewGraphWorkspaceCache()` between the two builds (a simulated restart), HEAD recovers `trap_here_fn`, so the loss lasts for the rest of the process. The LSP fallback can put the symbols back only when the file is open in a warm LSP. It never puts back the file's import edges, and F3 shows what that costs.

Remedy (a sketch): treat a file degraded by a wasm failure as dirty for the next build, so the next build re-extracts it instead of reusing the entry. Combined with F1's per-input keying, this gives one retry for a transient trap and a charge to the file for a trap that always happens.

### F3 (medium; catalog shape 10): a contained trap is silent on the turn-end surface, and a dependent's trap silently empties the cascade

Pre-fix, the cascade reported `indeterminate` / `error`, which is honest. Post-fix, the trapped file's missing data reaches no rendered surface. `wasm-trap` is a ledger count that `/lens-perf` and `pilens_health` pull, plus a durable row in latency.log. The cascade marker producers (`clients/dispatch/integration.ts:1350-1370`: `mode === "skipped"`, `persistCoverage.partial`, untrusted build info) never read per-file `extractionCoverage`. The `graph_degraded` cascade branch this PR adds (`clients/pipeline.ts:2104`) is reachable only by a trap that escapes containment. The PR body itself says no production path now does that: a past-budget compile trap is caught again by the extractor's `init` catch. So the reporter's ask, "the turn-end gate can say degraded instead of error", is met only on an unreachable path.

Probe (real build, `computeImpactCascade(graph, b.py)`, c.py imports b and calls `trap_here_fn`):

```
clean:            neighbors=["c.py"] importers=["c.py"] indeterminate=undefined
b.py traps:       neighbors=["c.py"] importers=["c.py"] indeterminate=undefined   (importer edge survives)
c.py traps:       neighbors=[]       importers=[]       indeterminate=undefined   <- silent all-clear
```

When the dependent traps, the edited file's cascade is silently empty. Because of F2, that stays true for the rest of the process.

Remedy (a sketch): record the files degraded by a wasm failure on the build (a count is enough). When a build carries any, `computeCascadeForFile` sets `indeterminate: graph_degraded` with the existing detail string. This also gives `graph_degraded` a production producer.

## Attack-angle answers

1. **Misclassification.** RangeError (stack, DataView OOB, "index out of bounds"), TypeError, AbortError (DOMException) and a user "array index out of bounds" all return `undefined`. A user `Error` whose message contains the exact phrase "memory access out of bounds" is classified as `trap`. That phrase is V8's own trap text, so the risk is low. A user error containing "Aborted" is classified as `abort`, but that matcher predates this PR. The only new effect is that such an error in a consumer is now silenced instead of rethrown, and it still poisoned the process pre-fix. No `Aborted` string exists in `clients/`. An object whose `toString` throws makes the classifier throw; the old matcher did the same.
2. **Post-trap trust.** A real in-process trap (a copied tree with a wild pointer, then `rootNode`) is a `RuntimeError` and degrades to `{parsed:false}` with one `wasm-trap` row. A post-trap parse matched the baseline symbols exactly. That proves nothing about corruption, because an OOB read corrupts nothing. A use-after-free probe (a dangling tree handle after `delete()`) silently read the next tree's `class_definition` without trapping. Stale pointers produce silent wrong trees, and a trap is only the out-of-bounds tail. Neither the fix nor pre-fix code can detect that. The recycle leaves the Language objects and the extractor's memoized Queries in place. For heap-state traps the fix is strictly more conservative than pre-fix, which had no bound. For input-caused traps it is strictly more aggressive (F1). Budget 3 with no re-arm is consistent with `wasmAborted`, but only once F1's per-input keying exists.
3. **Surface.** `wasm-trap` is in the union, and the coverage and order sweeps pass on the merge. It is not rendered at turn end (F3). `graph_degraded` renders distinctly from a clean build, but nothing reaches it (F3).
4. **Abort to NOT_PARSED.** I read every caller: `blocker-freshness` (`[]` before and after, and it memoizes `[]` as before), `module-report` (error text changes from the raw message to "tree-sitter failed to parse as X"), `read-expansion` (no expansion instead of a rejection), `complexity-client` (null both ways), the fact providers (coverage `unavailable`) and builder. None retries on the throw. Poisoning is unaffected, because `reportWasmAbort` still runs before the return.
5. **Language.load.** Behaviour is unchanged: pre-fix, a trap already returned false from `reportWasmAbort` and went to `recordGrammarLoadFailure`. The `decodeFailedGrammarPaths` stamp stops re-trying an unchanged file. The PR adds no new loop.
6. **Per-site table.** All 14 `reportWasmAbort(` sites plus the runner match the code and the verdicts. Two sites (`:2041` batch, `:4829` `runQueryOnFile`) still turn a trap into "no matches" for the runner. The body says so ("still swallowed"), and it predates this PR.
7. Covered by the red run and the mutation table above.
8. **Glossary 18→10.** This is a legitimate re-pin, not a dodge. The glossary retires `error` only where the delivery tier is meant (AGENTS.md:156). These are exception parameters in two functions the PR rewrote, the change shrinks the pin, and the sweep's own STALE output demands it. The merged glossary sweep is green. The `importOriginal` spread in the runner doubles is faithful to production, and `vi-mock-export-sweep` and `latency-logger-mock-shape` pass on the merge.
9. **Merge.** origin/master is now `327cc3a22` (#3610), which touches `degradation-ledger.ts`, `pipeline.ts` and the glossary pins. The merge with HEAD auto-merges cleanly. After the build on the merge, 14 suites ran (glossary, pipeline, both new suites, runner, grammar-load, kind coverage and order, vi-mock, latency-logger mock-shape, flake-shape, init, abort-degrade, dispatch-pipeline-formal): 286 passed and 1 failed.
