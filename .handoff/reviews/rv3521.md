## R2-F1 (medium-high): a requeued deferred record from branch X is credited on branch Y

**Where the epoch is captured.** Each settle captures it at entry: `index.ts:3618`, and `runtime-agent-end.ts:161` when the argument is absent. A deferred record carries no epoch of its own. The drain's requeue branches keep the X record in the queue:
- `"abort"` at `runtime-agent-end.ts:404` and `:708`;
- `"autofix-failed"`, `"format-failed"` and `"clients-unavailable"` at `:428`, `:738`, `:758` and `:775`;
- the 10-minute stale-orphan claim.

The next settle drains that record after the move and passes the post-move epoch. So `recordWritten(F, {branchEpoch: current})` is accepted, and F reads as authored on Y.

**The common trigger.** A user sees a run going wrong, then commits a `/tree` while the agent streams. pi's selector calls `abort()` first (`interactive-mode.js:4404`). `agent_settled` then fires with an aborted `ctx.signal`, and the drain requeues every pending record. After that, `navigateTree` runs. The next run on Y drains X's records. This is more common than the round-1 race, because it needs no timing window. It only needs the aborted run to have edited a file that has a deferred format or autofix pending.

**Probe.** Source: `probe-requeue.test.ts.txt`. It runs against the real `handleAgentEnd` and `RuntimeCoordinator`, with the formatted file backdated so the mtime fallback cannot be what allows the edit. The steps:
1. X queues a format.
2. An aborted settle requeues it.
3. `retainBranch` runs (the `/tree`).
4. The next settle runs with the epoch captured at entry, as `onAgentSettled` passes it.

Results:

```text
bfefa1c3c and the master merge 9fffe30cc, identical:
RQ-CONTROL  block    (/tree, nothing requeued)
RQ-REQUEUE  allow    (X's requeued format drained on Y: F never shown on Y, zero-read edit allowed)
```

**Model.** `Settle` takes the epoch when it dequeues, and nothing can put work back. I added one `Requeue` action (queued drain → not queued, work pending again; see `probes/md.py`). `TreeDrainFenced` then reports violated `NoBlindAllow` (15142 states). The trace is Settle, Tree, Requeue, Settle, Drain.

**Ask (ladder rung: the same seam, move the capture to where the work is created).**
- Stamp the branch epoch on the deferred record when it is queued. That happens at `deferMutation` and `deferFormat`, in-turn, so the value is the epoch of the branch whose edit queued it.
- The drain passes the record's epoch to `recordWritten`, and uses the settle's epoch only for records that have none.
- The requeue branches already copy the record with `...record`, so the epoch survives a requeue.
- Coalescing (catalog shape 55): when Y queues F again, the record should take the newer epoch. Y's own edit of F implies Y read F, so crediting that format on Y is correct. Keeping X's epoch would fail closed instead (a false block).
- Keep the settle capture for the sweep, whose entries are created inside the settle.
- Add `Requeue` to the model, with a before-fix config.

This is a shape, not verified across callers. The fixer should list every place a `DeferredMutationRecord` is created or merged.

## Adversarial questions from the brief

1. **Re-run of `probe-settled-race`.** RACE now BLOCKs. CONTROL and RACE-NODRIFT still BLOCK. This holds on both the head and the merge.
2. **Foreign bridge entry without an epoch.** Yes, it is treated as current, and a stale foreign write does allow a blind edit.
   - Probe: a second extension's `agent_settled` handler awaits a gate, then calls `getMutationBridge().recordMutation({filePath: F, kind: "write"})` after the `/tree`.
   - Results: `FB-CONTROL BLOCK`, `FB-RACE ALLOW`.
   - This is the pre-existing bridge policy: any reported write is credited as authored, and with no `/tree` at all the same edit is ALLOW. So `/tree` makes it no worse.
   - The body's writer table calls it "current by definition". It is really a residual of the same family as MD2: a foreign extension's deferred work that straddles the move. It belongs in the named-gaps list. Contract only.
3. **Epoch per read-guard instance, across fork and import.**
   - `RuntimeCoordinator` sets `_readGuard = null` on reset (`runtime-coordinator.ts:549`), so each session's guard starts at epoch 0. The fence therefore does not also cover session replacement.
   - The drain has its own session fence, `session.guardedWrite`. The settled sweep's bridge replay has none, even after G5, which fences only the refresh.
   - Probe NS: the settle is in flight during `runtime.newSession()`, with drift on a file read in the old session. Results: `NS-CONTROL BLOCK`, `NS-RACE ALLOW`. That holds on the head, the merge, and `origin/master` `df5fb8abb` itself (the master run also showed ALLOW for CONTROL, RACE-NODRIFT and RACE, as expected before #3521).
   - So this is pre-existing and not caused by this PR. It is a separate issue to file.
   - A one-line class fix: seed `branchEpoch` from a process-wide counter (`getProcessSingleton`), so a capture from an old guard can never equal the new guard's epoch. That would also fence the sweep across `/new`, fork and resume. I am naming this, not demanding it here.
4. **Concurrent secondaries.**
   - A secondary's `onAgentSettled` still runs the sweep (only the drain is skipped). It captures the shared guard's epoch, and a primary `/tree` during it refuses its writes, which fails closed.
   - A secondary's `/tree` never bumps the epoch, because it is gated.
   - Nothing new here.
5. **Does capture at settle entry cover sweep entries recorded before the settle?**
   - Sweep entries are all created inside the settle, after the capture. RF3 and RF4 below prove that wiring.
   - The observed replay in `tool_result` is in-turn. A timed-out observed settle is discarded, never recorded.
   - Deferred records queued before the settle and requeued across settles are not covered. That is R2-F1.
6. **Bridge API back-compat.**
   - `isValidMutationEntry` ignores unknown keys, and the bridge stays at `version: 1`, so an older pi-lens ignores the new field.
   - An older producer omits it, and the write is treated as current.
   - The new field is not type-checked. A foreign `readGuardBranchEpoch: "0"` makes the write be refused and logs a misleading `read-guard-write-after-branch-move`. That is harmless, because it fails closed for the reporter only.
   - Optional: validate it the way `provenance` is validated.
