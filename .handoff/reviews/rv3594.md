## Findings

### R2-F1 (High, correctness). `tailMaxSeq` returns a max below the file's true max when a higher seq sits before the window. The next allocation then reuses a seq already in the log.

- Where: `clients/project-changes.ts`, in `tailMaxSeq`'s trust rule `max === lastLineSeq || start === 0`.
- The rule only detects disorder inside the window. If the whole window is locally increasing, the rule trusts it, even when an earlier line holds a higher seq.
- The body claims the scan converges "exactly when disorder is actually present". The Observability section also claims item 2 produces "the same values". Both claims are false.

The probe uses a fresh `RuntimeCoordinator` and the real `recordProjectMutation({ cwd })`, with the cursor unseeded:

| Log shape | head `7dea4cd` | origin/master `df5fb8a` |
|---|---|---|
| S1: seq 1..1000, then 30 lines of seq 5..34 | allocated **35** | allocated 1001 |
| S1b: one seq-900 line, then 25 lines of seq 1..25 | allocated **26** | allocated 901 |
| S4b: 50 lines, then a 20 KB-long seq-500 line, then seq 51 | allocated **52** | allocated 501 |

Each head allocation is a duplicate: seq 35, 26 and 52 are already in the log. That breaks #3511's `uniqueSeqs` invariant.

Is this reachable? Yes, in exactly the logs this optimisation targets:
- #3511 (`1112f3aa3`) is not in any release; `v4.3.0` does not contain it.
- Every released version appends `seq` from its own runtime counter (`v4.3.0:clients/runtime-coordinator.ts:668`, `appendProjectChange(args.cwd, { seq: projectSeq, … })`).
- So every existing log written by two concurrent sessions can already hold "A wrote M+1..M+500, then B wrote M+1..M+30". Sessions still running v4.3.0 after the upgrade keep producing that pattern.
- The tail scan runs on the unseeded path, which is the large-log, timed-out `session_start` case. Until the async read lands and merges, allocations start from the stale tail max.

The fast-check property cannot see this:
- Its oracle asserts `monotonicLog`, so the world it models never contains disorder.
- It never reaches the trust rule; see R2-F4.

Remedy (a shape, not verified):
- No bounded tail scan equals the full-file max on a log that allows disorder. Trusting the tail needs a durable witness that the log is monotone up to that point.
- One option is a sidecar written under the change-log lock: it records the max seq and the byte offset it covers, and is invalidated by any `unlocked` append. The tail is trusted only when the sidecar covers the file. Otherwise the full read runs, and establishes the sidecar.
- The other option is to take item 2 out of this PR and file it with that design note.
- Either way, keep `refs #3594`, not `closes`, until this is resolved.

### R2-F2 (High, correctness). A torn last line is lost for good, and the next allocation reuses its seq.

- Where: `readChangeLogMaxSeq`'s tail branch sets `cursor.bytes = size`.
- `size` includes a trailing partial line. The forward path instead stops at the last newline, per its own comment "a line still being written … is read next time".
- When the partial line completes, the next read starts mid-line, cannot parse the remainder, and drops that line's seq.
- The race this opens: the pre-lock read (#3577) runs outside the lock. So a sibling that holds the lock and is mid-append is exactly the writer being read.

Probe S2: the log holds lines 1..3 plus the first 40 bytes of a seq-4 line. The first `appendProjectChangeAllocated` call runs the tail scan; I injected an abort inside `build`. The sibling then finishes its line, and a second call follows.

| | logMaxSeq handed to `build` | seq allocated |
|---|---|---|
| head | **3** | duplicate 4 |
| origin/master | 4 | 5, correct |

Fix, verified on the built JS:
- Have `tailMaxSeq` return `{ max, bytes: start + buf.lastIndexOf(0x0a) + 1 }`, and set `cursor.bytes = tail.bytes`.
- Compute the offset from the buffer, not from the decoded string. A window that starts mid-way through a multibyte character decodes to U+FFFD, and the string's byte length then drifts.
- With that patch, S2 hands `build` the value 4. The three change-log suites still pass (46/46).
- It needs a red-first test that makes the log end in a partial line, runs the tail scan, completes the line, and then allocates.

### R2-F3 (Medium, standards: observability). The new seam leaves no record.

- The tail scan has no success-path record, and its silent fallback to the full forward read has none either. That fallback is the roughly 1 s case the change exists to remove.
- A live monitor therefore cannot tell whether the tail scan ran, grew its window, or fell back.
- The body answers observability for item 2 with "no new failure path … producing the same values". R2-F1 and R2-F2 disprove that.
- Ask for a `logLatency` phase that records the outcome (`tail` / `grown` / `fallback`), the window size and the elapsed time.

### R2-F4 (Low, test coverage). The property test never exercises the trust rule.

I instrumented the built `tailMaxSeq` and ran `project-changes-seq-properties`:
- It made 198 tail-scan calls, all with `start=0`. The largest log was 220 bytes, a single line.
- The same happened with the window cut to 8 bytes: the trust rule (`start > 0`) was never reached.

So the property says nothing about item 2. The unit tests do pin behaviour: T1, T2 and T3 below all go red.

### R2-F5 (Low). Once the lease runs out, the switch from the busy shape to the legacy shape costs one more full wait.

- `aged#0` paid 2002 ms, and later calls skipped.
- The cause: the identity remembered from the busy timeout (`lock.<n> …`) is not the legacy identity.
- That is one extra wait per stuck episode, which is acceptable. It is noted so that the "wait once" test title is not over-read.

## Item 1 (round-1 F1 and F2): verified fixed

- Can the bridge identity produce a false skip? The contents are `${pid}:${Date.now()}:${randomUUID()}`, in this version and in v4.3.0 alike. Every acquisition is therefore unique, so no identical re-take can occur.
- Residual edge: the create-then-write gap can leave the file empty, and an empty read then yields the identity `"legacy "`. Two such reads a microsecond apart could match across holders. That is theoretical and not a finding; treating empty contents as `undefined` would close it.
