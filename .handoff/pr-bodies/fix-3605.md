## Why

A web-tree-sitter runtime trap in one file's symbol extraction now costs that file its tree-sitter symbols, not the whole review-graph build and the per-edit cascade verdict.

## Notes for the reviewer

- **Merge order:** based on `origin/master` at `df5fb8abb`, which already contains #3602 (the other recent PR touching `clients/pipeline.ts`, `tests/clients/pipeline.test.ts` and the glossary sweep). A merge check of this branch with that master was clean and green before the rebase: 10 files, 176 passed (glossary sweep, pipeline, both new suites, runner, grammar-load, degradation-kind order and coverage, vi-mock sweep).
- **Behaviour change beyond traps:** an Emscripten *abort* thrown inside a `withParsedTree` consumer now degrades that file to not-parsed instead of rethrowing, as an abort during the parse already did. `tests/clients/tree-sitter-client-init.test.ts` pinned the old rethrow; that pin is flipped (see Tests). An abort still poisons the process exactly as before.
- **Recovery is bounded, and honest about what it can do.** web-tree-sitter caches its single Emscripten module (`initializeBinding` in `web-tree-sitter/tree-sitter.js` 0.25.10 returns the cached `Module3`), so no in-process re-init exists. On a trap the client drops its parsers and clears its tree cache (the pi-lens-owned wasm objects that carry state across files), counts the trap, and after `WASM_TRAP_BUDGET` (3) traps treats the next one as an abort: tree-sitter is off until restart, with the existing `wasm-abort` record and user notice. The budget is process-lifetime like `wasmAborted`, because the heap outlives sessions.
- **Maintainer decision:** the budget value 3 is a judgement, not a measurement. The reporter's log shows dozens of traps per workspace, but not how many fell in one process.
- **Maintainer decision:** a trap during `Language.load` stays charged to the grammar file (re-fetch path), not to the process-wide budget. Otherwise one bad grammar could poison every language.

## Summary

Fixes #3605. `isTreeSitterWasmAbortError` matched only `Aborted` / `abort()`, so a wasm runtime trap (`table index is out of bounds`, `memory access out of bounds`, `null function or function signature mismatch`) classified as nothing. A trap raised by `query.matches` in the symbol extractor's `queryMatches` was reported and rethrown, then reported and rethrown again by `parseFileAndUse`'s consume catch. That rejected `_doBuildGraph`, logged `build_failed`, and turned the per-edit cascade into `cascade_indeterminate` / `error`. The pre-fix red below reproduces that exact stack through the real build: `Query.matches` -> `queryMatches` -> `extract` -> `builder` -> `parseFileAndUse`.

What changes:

1. One classification seam, `classifyTreeSitterWasmError` (`clients/tree-sitter-client.ts:274`). The abort message is tested first, because Emscripten's `abort()` throws a `WebAssembly.RuntimeError` too. Then `instanceof WebAssembly.RuntimeError` is the trap test, and three V8 trap messages are its fallback for a rewrapped or cross-realm trap (`clients/tree-sitter-client.ts:261`).
2. Containment: `parseFileAndUse`'s consume catch degrades any wasm failure to `NOT_PARSED` and still rethrows anything else (`clients/tree-sitter-client.ts:1740`):

```ts
if (classifyTreeSitterWasmError(error)) return NOT_PARSED;
```

   `extractTreeSitterSymbols` then returns its empty, coverage-unavailable result, and `addFileToGraph`'s existing zero-symbol LSP fallback runs for that file.
3. Recovery and bound, in `reportWasmAbort` (`clients/tree-sitter-client.ts:626`):

```ts
if (++this.wasmTraps <= WASM_TRAP_BUDGET) {
```

   Within the budget a trap records `wasm-trap` with `incrementDegradationCount`, drops the parsers without deleting them (a caller may hold one across the `await` in `parseFileAndUse`; the leak is capped by the budget), clears the tree cache, and returns `false`. `reportWasmAbort`'s return still means "the runtime is dead", so every other call site keeps its own non-fatal path. The trap past the budget takes the existing abort path. A trap object is counted once however many sites report it (`clients/tree-sitter-client.ts:623`):

```ts
if (this.reportedTraps.has(thrown)) return this.wasmAborted;
```

4. If a trap still escapes to the build's catch, `build_failed` carries `failureClass` (`clients/review-graph/builder.ts:6062`), and the pipeline's cascade catch reports it as `graph_degraded` rather than `error` (`clients/pipeline.ts:2104`).

### Failure list (written before the first edit)

Classifier: C1 a `RuntimeError` trap is not classified (the defect). C2 an abort, itself a `RuntimeError`, is classified as a trap. C3 a non-wasm consume error is classified as wasm and silenced (shape 10). C4 a trap message on a plain `Error` is missed. C5 a `RuntimeError` with an unlisted message is missed (shape 34).
Containment: K1 a trap in consume still rethrows. K2 a non-wasm consume error stops rethrowing. K3 the build completes but loses the other files' symbols. K4 the trapped file keeps a partial symbol set, so the LSP fallback is not consulted.
Recovery and bound: R1 the first trap poisons the process. R2 traps never escalate. R3 one trap is counted twice (`queryMatches`, then `parseFileAndUse`). R4 the trapped parser or cached tree is reused. R5 recycling frees a parser a concurrent caller holds. R6 a session reset re-arms the budget. R7 a trap in `Language.load` is charged to the budget.
Observability: O1 a contained trap leaves no record. O2 escalation leaves no `wasm-abort` record or notice. O3 `build_failed` carries no classification. O4 the cascade reports `error` for a wasm failure.

Each row is covered by a test named in the Tests table. R5 is prevented structurally (parsers are dropped, never `delete()`d), not tested: a concurrent-holder test would need a parser double, and the pre-fix code never freed parsers either.
