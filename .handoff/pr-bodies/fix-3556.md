## Summary

Three new `guard-bash.mjs` `DenyRule`s (`scripts/hooks/guard-bash.mjs:150`), batched as tracking issue #3518's G12:

- **`sharedKill` (closes #3556, `scripts/hooks/guard-bash.mjs:1285` `classifyPkillKillall`)** — `pkill`/`killall` match machine-wide by default; #3506's fixer ran `pkill -f tlc2.TLC` to stop its own TLC run and may have killed a concurrent session's run too. Denied unless `pkill -f` is scoped with a pattern that contains the PreToolUse payload's own `cwd`, AND `cwd` is itself a linked worktree (review F6) — the shared main checkout's own path is a prefix of every worktree's path, so scoping to it alone would still match every worktree's TLC. `killall` is never scoped: it matches by process name only, with no full-command-line mode a path could appear in. `kill <pid>` is untouched (a different command). `kill $(pgrep -f …)`/`pgrep -f … | xargs kill` are a documented blind spot (review F6).
- **`tmpCheckout` (closes #3526, `scripts/hooks/guard-bash.mjs:1044` `classifyGit`, `:1183` `classifyMktemp`)** — `git worktree add`, `git clone`, and `mktemp -d` (bare, bundled short flags, `-t`, `-p`/`--tmpdir=`) are denied when the destination resolves under `/tmp` (tmpfs on the maintainer host; ~20 accumulated review/merge scratch checkouts filled it to 8/8 GB swap). Resolution follows variable indirection (`S=/tmp/…; W=$S/wt; git worktree add $W` — the actual shape of every historical `/tmp` worktree-add in the corpus, review F1) and expands a leading `~` from `HOME` (review S1), both bounded to a small hop cap; a literal `$TMPDIR`/`$TMP`/`$TEMP` prefix is substituted from the command's own env assignment, then this hook's own `process.env`, then `/tmp`. `mktemp` for a plain file is always allowed, and `.claude/worktrees/`, `~/.cache/pi-lens-orchestrator/worktrees`, `~/.local/share/pi-lens-orchestrator/tmp/`, `~/.plegma/work` stay allowed.
- **`checkUngated` (refs #3471, `scripts/hooks/guard-bash.mjs:1789` `findUngatedWriteInChain`)** — a `git commit`/`git push` segment whose NEAREST preceding check (`npm run lint`/`build`/`test`/`fmt:check`/`preflight`, `npx vitest`, a bare or `timeout`-wrapped `vitest` resolved by basename, `npm test`/`t`, `tsc`, `node scripts/check-*.mjs`) is not connected to it by an unbroken `&&` chain is denied. The backward search for that nearest check stops at an earlier write (so `commit -m x; git status`, with no check anywhere, is never judged) and exempts a write PER-WRITE, not per-region (review F3), when walking backward from it reaches an unmatched control-flow opener before a closer (this repo's own `vexit=$?; if [ $vexit -eq 0 ]; then …; fi` convention, unmodeled rather than guessed at).

**Case 3 remainder**: #3471's issue body quotes a third incident, `git push … >push.log 2>&1; echo push=$?; grep … push.log`, with no check anywhere in it — the literal proposed rule ("a write follows a check through `;`/`|`") does not reach it. I considered a general "a write must be `&&`-only or command-final" rule and rejected it: it would ALSO deny `git commit -m x; git status`, an ordinary sequential status check after a commit (pinned as an ALLOW case, `tests/scripts/guard-bash-hook.test.ts:364`). `refs #3471`, not `closes`; the issue comment posted alongside this PR names this remainder AND (review F7) the issue's own ask for an opt-out mechanism when a check's red is the intended, sanctioned outcome (e.g. a test asserting a lane's own failure path) — that opt-out is not implemented in this PR; it is a design decision for the maintainer (see hand-back).
