## Summary

**#3497** — `scripts/ci-verdict.mjs` shelled out to `gh` unconditionally, so a Claude Code cloud container (no `gh` binary, but `GH_TOKEN`/`GITHUB_TOKEN` set) exited 70 on every read. #3491's verify reviewer had to read CI by hand instead, and misread a *cancelled* run as green from a `check_suite.completed` wake.

`run()` decides a transport once, before any repository/PR resolution (`scripts/ci-verdict.mjs:1302`): `resolveTransport(ghExec === gh, resolveGithubToken())` (`:1131-1134`). Only when the caller left `ghExec` at its real default (never for an injected test double), the real `gh --version` probe confirms `ENOENT` (`isGhMissingError`, `:244-246`), and a token is present does it switch to REST. On REST, `resolveRepositoryViaGit()` (`:941`) reads `git remote get-url origin` instead of `gh repo view`, and `restResolveHeadSha`/`restFetchCheckRunsPayload`/`restResolveRequiredCheckNames` (`:1056`, `:1073`, `:1100`) read the exact same endpoints `gh api` was already calling, via an authenticated `fetch` (`restGet`, `:967`). `extractRequiredCheckNames` (`:873`) was pulled out of the existing `resolveRequiredCheckNames` unchanged so both transports share the one branch-protection parse. The printed verdict names its transport (`Transport: gh` / `Transport: rest`, `:1394`).

Two things the REST path does NOT do the same as `gh`, both intentional and both stated here rather than left implicit: it never runs `resolveClassification`/`fetchRerunState` (no REST path was added for those — #3497's acceptance criteria are PR head/mergeable, check-runs and required-check names only), so an infra-classified PR with a rerun in flight reads differently on the two transports (REST: no rerun grace, `computeVerdict` treats it as an ordinary failing check; `gh`: the rerun grace applies) — the direction is fail-closed (REST never grants a pass the `gh` path wouldn't also grant). And `main()`'s proxy handling (Round 2, below) means the REST transport needs Node >=22.21 to work through a proxy at all; below that version it fails closed with an explicit message rather than attempting REST and misreading the result.

Every acceptance criterion is met: the red-first proof below is a real run against this sandbox (no `gh`, a real token); the four fixture shapes (green head, failed required check, absent required check, cancelled required run) are proven to reach the SAME `computeVerdict` exit code through the REST fetch function as they already do through the gh-shaped equivalent (that equivalence is the whole of `ci-verdict.test.ts`'s 132 tests, all still green after this change); the transport line is printed and asserted; and (Round 2) a real end-to-end run against the real GitHub API, through the real proxy, is quoted below.

**#3563** — on 2026-09-26 the orchestrator filed about a dozen follow-up issues through the GitHub API (#3543-#3546, #3548, #3549, #3552, #3556, #3558-#3560) with no TYPE label and no `priority:*` label, since API creation bypasses the issue templates that would otherwise force one. `.github/workflows/untriaged-issues.yml` runs `scripts/detect-untriaged-issues.mjs` daily and fails, listing every open issue missing either — `scripts/lib/label-triage.mjs`'s `isUntriagedIssue` (`:103-109`) flags an issue missing its `priority:*` label, or (unless its title is `tracking:`-prefixed, per the issue's own exemption) missing its TYPE label too. `TYPE_LABELS` (`:73`) is derived from `.github/labels.yml`'s own "# Type labels" block rather than hand-copied, so it can't silently drift from the manifest label sync already treats as authoritative (#2553's own single-source-of-truth lesson).

All four acceptance criteria are met: the red/green transcripts below are the check's own output against a fixture with an unlabelled issue, before and after labelling; a mutation table (each direction of every new guard) is quoted below; and the merge-train mistake row is added (`.claude/skills/merge-train/SKILL.md`, tail of the "Common mistakes" table).
