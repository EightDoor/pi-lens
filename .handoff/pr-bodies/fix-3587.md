## Why

## Summary

`deregisterInstanceRootNow`'s sync-only lock attempt (`withInstanceRegistryLockSync`) gave up after 500ms with no retry when this process's own heartbeat (or a registration) held the registry lock, or a peer held it past 500ms. A declined secondary worktree's root then stayed in `instances.json`'s `projectRoots` for as long as the host session lived — the sibling of the exact bug #3498/PR #3593 fixed in `deregisterInstance`, on the function PR #3593's own class sweep named and left (`clients/instance-registry.ts:1064` in that PR's body, quoting a probe transcript with `lock timeouts=1` and the root still present).

The fix reuses G2's mechanism exactly as the issue prescribes: on a failed sync attempt, fall back to the async lock waiting through `LOCK_WAIT_THROUGH_LEASE_MS` (5.5s: the lock's stale lease plus one ordinary wait), and key every lookup and whole-entry removal through `isOwnEntry`/`withoutOwnEntry`. The one structural difference from `deregisterInstance`'s fix: `deregisterInstanceRootNow` already runs on the registry tail (`deregisterInstanceRoot` queues it), so unlike `deregisterInstance` — which runs off the tail, synchronously, at `session_shutdown`, and must queue a NEW tail entry to retry — the fallback here just continues in place, on the same tail slot, so the ordering guarantee (the next queued op lands behind it) holds by construction with no new queueing logic.

`planRootRemoval` factors the decision (which write, if any, and whether to re-arm the heartbeat's repair intent) into one pure function called once per real lock acquisition, so the sync path and the queued path can never disagree about what a given read should produce. This keeps PR #3593 round 1's F1 gate (`if (generation.isCurrent()) rememberRegistrationRoot(...)`, `clients/instance-registry.ts:1119`) exactly as shipped — the check still runs once, at the point of the actual write, whichever path got there.

Closes #3587. Both acceptance criteria are met: the regression test replays the issue's own overlap (shutdown/removal meeting this process's own heartbeat hold) and is red on pre-fix code; the root is removed once the hold releases, proven by both the own-hold case and a second case where a peer's hold outlives the sync wait and one ordinary async wait (matching `deregisterInstance`'s own peer-hold test) but resolves inside the lease.

**Plus one G16-of-#3518 scope addition that shipped (see its own section below), `refs #3518`/`refs #3602`, not `closes`:**

1. **`updateHeartbeat` now shares the registry mutation tail** with `registerInstance`/`registerInstanceRoot`/`deregisterInstance`, closing a race where a heartbeat landing between session_start's registration setting its repair-intent and that registration's own write lands recorded a spurious `instance-registry-registration-missing` (the CI red on PR #3602). This also makes the #3587 own-hold scenario above unreachable for the ROOT-removal/heartbeat pairing specifically — see the Failure list F1 row.

**A second scope addition (exit-time generation release for the `index-wiring` dead-pid lock) was attempted and then dropped in review.** The G16 review (`scratchpad/rv3587/REVIEW.md`, finding F1) showed the `process.on("exit", ...)` listener added in commit `b91754357` never runs on the path that actually leaked the lock: vitest's fork pool kills its workers with `SIGTERM`, and Node does not emit `"exit"` on a default-signal death — the listener only ever helped a graceful `process.exit()` call, which is not what killed the leaking worker. That commit, its tests, and its changelog fragment are reverted in this PR (see "Scope addition 2 (reverted)" below for the full finding and the revert). No production signal handler is added in its place. **The dead-pid lock residue is filed separately (#3617)**, with a test-side mechanism (a registry-tail drain) rather than a production exit hook. A related simplification the review surfaced — collapsing `deregisterInstanceRootNow`'s sync-then-fallback into one lease-waiting lock, removing the 500ms event-loop spin — is filed as **#3618** and not done here (see "Notes for the reviewer" above).

## Scope addition 1: heartbeat vs. queued registration race (refs #3602)

**Not a GitHub issue — a scope addition named directly in this task's brief, citing the PR whose CI it reds.** `gh issue view 3587`/`gh issue view 3518` carry no comment naming this addition (checked, per the standing procedure for a scope addition arriving as a message); it was handed to me as part of the ORIGINAL task brief for this round, not a mid-task addition arriving after work began, so the "mirrored on the issue" check does not apply the same way — noted here so the maintainer can see the provenance is the brief itself, not an issue comment. PR #3602 (`fix(session): keep session-straddling writers in their session`, unrelated to the registry) hit CI-red on `tests/index-1892-scanner-freshness-witness.test.ts` from this race; `origin/master` (merged into this branch below) already carries a test-side mitigation for that one golden (`await _settleRegistryMutationsForTests()` right after `session_start`, citing "the race itself is G16's (#3587)") — left in place: harmless now (settling an already-drained tail is a no-op) and not this PR's diff to remove.

**Why.** `registerInstance(root)` is queued via `queueRegistryMutation` (the in-process registry-mutation tail); inside the queued op, `registerInstanceNow` calls `rememberRegistrationRoot(projectRoot)` — which sets the process-wide repair-intent root — BEFORE its own write lands (the write needs the registry lock, a real fs-backed acquisition, and only runs after that). `updateHeartbeat` used to take the registry lock directly, bypassing the tail entirely. A heartbeat that won the race to the lock in that gap read the registry before the registration's write, found no own entry, and — because the intent was already set — recorded a spurious `instance-registry-registration-missing` and queued a redundant `registerInstance` re-call, on an entirely ordinary first turn.

**Fix.** `updateHeartbeat` now queues its body (`updateHeartbeatNow`) through the SAME `queueRegistryMutation` tail as `registerInstance`/`registerInstanceRoot`/`deregisterInstance`'s fallback, so submission order becomes execution order: a heartbeat queued behind a still-in-flight registration can no longer run until that registration's mutation (write included) has fully resolved. `clients/instance-registry.ts:602` (`updateHeartbeat`) / `:608` (`updateHeartbeatNow`).

## Scope addition 2: exit-time generation release (#3518 G16 residual 2)

**Why.** A whole-file `tests/index-wiring.test.ts` run leaves the shared `.probe-home` registry lock's top generation held by the vitest fork worker's own DEAD pid — reproduced directly (not just from the task brief): 3/3 standalone whole-file runs against a fresh `PI_LENS_HOME` before this fix left the top generation (`lock.14`, `lock.14` etc. across runs) with no `.released` marker, owned by a pid `ps -p <pid>` could no longer find. Root cause: several registry mutations are fire-and-forget by DESIGN (session_start's `void registerInstance(...)`, turn_end's `void updateHeartbeat()`, and `agent_settled`'s quiet-window `instance_registry_heartbeat` task, which `clients/quiet-window.ts`'s own docstring says is deliberately "kicked off unawaited" so a slow handler never delays the SDK's `_runAgentPrompt`). When the vitest fork-pool worker process exits at the end of a whole-file run (via a forceful `process.exit()`, which abandons pending promises/timers without running their `finally` blocks), a mutation still mid-flight through the registry lock — having created a generation but not yet reached its own `finally { release(...) }` — leaves that generation's marker owned by the now-dead worker pid. Every later process in that shared home then pays an avoidable `instance-registry-lock-stale-takeover` degradation for a hold this same process could have released cleanly on its way out. This is registry/lock code (`clients/instance-registry-lock.ts`), so per the brief, fixed here — not purely a test-harness issue, since the same fire-and-forget shape (documented as intentional) can leave a REAL pi-lens process's lock generation unreleased under any ungraceful `process.exit()` elsewhere in the process, not only in a test worker.

Not a correctness bug on its own: `pidFileIsStale` already judges a dead owner's generation stale on sight (checks the owning pid's liveness, not just the mtime lease), so the very next acquirer takes it over cleanly. This purely removes an avoidable cost.

**Fix.** `clients/instance-registry-lock.ts` now tracks every generation this process currently holds (`openHoldsState.holds`, kept on `globalThis` via `Symbol.for` rather than plain module state — the same reason `clients/ndjson-logger.ts`'s shared exit handler does this: Vitest re-evaluates the module after `vi.resetModules()`, and pi can load the source/compiled entry through separate module graphs, so a module-local guard would register one "exit" listener per graph and reproduce Node's `MaxListenersExceededWarning`) and releases them all from a single, synchronous, once-registered `process.on("exit", ...)` listener. `tryAcquire` (the ONE choke point both `withInstanceRegistryLock` and `withInstanceRegistryLockSync` already share) adds to the set on a successful acquisition and registers the listener (idempotent guard); `release` removes from the set on a normal release, so a generation this process already released cleanly is never touched again by the exit listener.
