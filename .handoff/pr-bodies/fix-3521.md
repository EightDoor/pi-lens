## Why

After `/tree`, `/fork`, `/clone` or a resume, the read-before-edit guard now credits exactly the reads the conversation still shows the agent, so edits the conversation never showed are refused and edits it did show are no longer falsely refused.

## Notes for the reviewer

- **The rule** (decided on #3521): after every conversation move, a read record is kept only when its tool call's `toolResult` is on `ctx.sessionManager.getBranch()`. It is kept whole, with no FileTime stamp, so each edit is checked line by line against disk. `/tree` also clears the edit history, `writtenThisSession`, pending creations and the FileTime stamps, and re-anchors the mtime fallback.
- **D1: tool-call id reuse is an ACCEPTED residual** (maintainer decision, mirrored on #3521). pi stores provider ids verbatim, and three providers can repeat them across responses:
  - Mistral's fallback derives `toolcall:<index>` (`@earendil-works/pi-ai` dist `api/mistral-conversations.js`, lines 518-520 and 120-129);
  - OpenAI-compatible completions store `toolCall.id || ""` (`api/openai-completions.js`, line 326);
  - Google makes ids unique within one message only (`api/google-generative-ai.js`, line 135).

  With these providers, a sibling branch's read can match an id that is also on the current branch. The test "credits a sibling branch's read that reuses the same tool-call id (accepted residual, #3521 D1)" pins that. Records with an empty or absent id are never matched (`resolveToolCallCorrelationId` returns `undefined` for `""`). The test "drops a read whose tool result carried no tool-call id" pins that.
- **D2: the fork hand-off keeps the 0 ms `session_before_fork` budget** (#2523, `NO_AWAIT_HOOKS` unchanged).
  - The primary channel is a process-wide slot (`getProcessSingleton`), because pi re-runs the extension factory for the fork.
  - The parent's sidecar is saved fire-and-forget. It is the fallback, and the only channel for `pi --fork <path>`.
- **Residuals** (accepted or named; each is pinned by a test or a TLC config):

| Residual | Cost | Pin |
|---|---|---|
| D1: a provider that reuses tool-call ids across branches | a sibling branch's read can vouch for an edit | test "credits a sibling branch's read that reuses the same tool-call id (accepted residual, #3521 D1)" |
| F2: a primary `/tree` clears a live concurrent secondary's reads, because the guard is the shared module-level `runtime.readGuard` | one re-read in the subagent, never an allow | test "wipes a live concurrent secondary's read on a primary /tree (accepted residual, #3521 F2)"; the follow-up is filed by the orchestrator |

## Summary

This PR closes #3521 under the rescope posted on the issue (comment 5850154751, plus the maintainer decisions in comment 5850423253).

**`/tree` was confirmed broken:**
- pi-lens had no `session_tree` handler, so every record, authored write, own-edit record and FileTime stamp from an abandoned branch stayed in force (blind and stale allows).
- The new handler `index.ts:2714` calls `ReadGuard.retainBranch` `clients/read-guard.ts:1549`.

**The `/fork` half was the opposite defect: it carried nothing.**
- pi re-runs the extension factory for the forked runtime. The closure-local `pendingForkReadGuard` died with the parent's activation, so the fork's `session_start` found no state and falsely blocked reads still in the conversation.
- The hand-off now rides a process-wide slot:

```

**Records now carry `toolCallId`:**

`clients/read-guard.ts:64`

```

### Failure list before code

Written from the diagnosis's §6 before the first edit. Each direction is a row in the mutation table below.

1. An abandoned branch's read, write or own edit still vouches for an edit (blind or stale allow).
2. A read the new branch still shows is dropped (false block): fork, clone, `/tree` onto a result entry, resume, `pi --fork`.
3. A kept record is re-stamped or re-hashed from today's disk, so it vouches for bytes the abandoned branch wrote.
4. A kept record is dropped whole because one of its lines changed (T5/F1).
5. The own-edit rescue, the authored-write escape or the mtime fallback survives a move.
6. The hand-off does not survive re-activation, or a stale hand-off is taken by the wrong session.
7. A concurrent secondary's `/tree` filters the primary's guard.
8. An unreadable session manager throws inside a session handler.
9. A version-1 or corrupt sidecar crashes `session_start`.
