## Why

`acquireBoundedPidFileLock` waited its full 2s budget on every call under a holder stuck past its 5s lease — the normal state of a real stall, not an edge case — so it now remembers that holder and skips the wait, a dead-code duplicate gate in the snapshot exit hook is gone, and a proposed change-log read optimization (item 2) was withdrawn this round after review found it unsound on logs that permit disorder.

## Summary

### Item 1 — `acquireBoundedPidFileLock` remembered-holder skip

Applies #3578's remembered-holder skip to the durable-store sync lock: the first try is always made; a later call that finds the same holder still there tries once and falls back exactly as a timed-out wait does (throw, or `null` under `skip-log`), instead of waiting its full budget again.

**Round 2 finding F1 (High, fixed).** The round-1 version keyed the remembered name on `topGenerationHolder` alone (the generation file's own identity). `acquireBoundedPidFileLock`'s generation has only a 5s lease and no heartbeat, so a holder stuck past 5s — the review's own probe shows this is the *normal* state of a multi-second stall, not an edge case — is taken over by the next contender's own always-run first try. That contender then finds the SAME live pid still holding the pre-#3476 bridge file and gets `"legacy-held"`, releasing its own fresh generation. From that point, `topGenerationHolder` names a NEW, released generation on every subsequent call — never matching the remembered busy-holder name — so the skip stopped firing again after roughly one lease, and every call after that paid the full 2s wait for as long as the holder lived.

Fix: `currentHolderIdentity` (`clients/bounded-pid-file-lock.ts:417-431`) names the CURRENT retry's own outcome — `topGenerationHolder` for `"busy"`, the bridge file's own contents for `"legacy-held"` — and both the skip check and the post-timeout memory write use it. A `"legacy-held"` retry always mints its own fresh generation on every iteration, so its `topGenerationHolder` name can never collide with a remembered `"legacy …"` name or vice versa.

**F2 (Low, fixed).** Mutation M6 (dropping `options.logContention()` inside the skip branch) stayed green under the round-1 test suite. In production that callback is actionable-warnings' `warning_state_write_dropped` emission per dropped write; `recordDegradationOnce` only fires once per session, so a missing callback would silence every later skipped write with nothing else to notice. The "ten calls" tests now assert `logContention` is called exactly 10 times.

**F4 (contract, fixed).** A test comment said "exactly one skip recorded" while its own assertion was `toBe(0)` — fixed to describe what the assertion actually proves.

**This round: review round 2's residual edge, closed.** The bridge file's create (`wx`) and its token write are separate steps, so a reader can meet it empty. `currentHolderIdentity` used to read an empty file as the identity `"legacy "` — a non-`undefined` string — so two DIFFERENT holders that each happened to be caught empty a moment apart could falsely match each other. Theoretical (the review itself called it "not a finding"), closed anyway: empty content is now treated the same as unreadable, `undefined`, which the skip's own `timedOutHolder !== undefined` guard already never matches. Red-first proof: a persistently empty bridge file was skipped on its SECOND call under the pre-fix source (`expected 0 to be greater than or equal to 500`); it now waits the full budget every time.

### Item 2 — withdrawn after review

**What was proposed and why it's gone.** Implemented #3577 option 3 (a bounded backward tail-scan for the change log's first-per-session read) across rounds 1-2, reaching a design that parsed every complete line in its read window and trusted the max only when it was the window's own physically last line, growing the window (converging to a full read) whenever an earlier line in the SAME window held a higher seq.

**Round 2 verify review found this insufficient — R2-F1 (High).** The trust rule only detects disorder INSIDE the window it has already read. A higher seq sitting BEFORE the window entirely is invisible to it. Probed: a log with seq 1..1000, then 30 more lines of seq 5..34 appended (a real shape: pre-#3511 — i.e. v4.3.0 and every released version — writers append `seq` from their own runtime counter, so any log two concurrent v4.3.0 sessions wrote can already look like "A wrote 1..1000, then B wrote 1..30") — the fix allocated **35**, a duplicate already in the log; `origin/master`'s plain full read correctly allocates 1001. The unseeded-cursor path this optimization targets is exactly the large-log, timed-out-`session_start` case where reading such a log cold is the normal case, not a corner case.

**R2-F2 (High).** Independently, the tail branch set `cursor.bytes = size`, which includes a half-written trailing line (the pre-lock read runs outside the change-log lock, so a sibling mid-append is exactly what it can read). The next read then starts mid-line, can never parse the remainder, and permanently loses that line's seq — the next allocation reuses it. Probed and reproduced on the built JS.

**No bounded scan can fix this.** Equaling the whole-file max on a log that permits this disorder needs a durable witness that the log is monotone up to some point — not just a snapshot of one window. The fast-check property suite (`project-changes-seq-properties.test.ts`) never caught either bug because its own model (`monotonicLog`) asserts the world it generates never contains disorder in the first place — it structurally cannot reach the trust rule with a violation.

**Withdrawn per the maintainer's decision.** `clients/project-changes.ts` and `tests/clients/project-changes.test.ts` are reverted to `origin/master`'s exact content (verified: `git diff origin/master -- clients/project-changes.ts` is empty). The item-2 changelog fragment is removed. A durable design — e.g. a small sidecar, written under the change-log lock, recording the max seq and the byte offset it covers, invalidated by any `unlocked` append, with the tail trusted only when the sidecar covers the file — goes back to the maintainer as a separate follow-up rather than being rushed into this PR.
